QUIZ MASTER — GAME-BY-GAME PLAN
================================
This file tracks what needs to be done to support creator-configured
quizzes for each game. Each entry covers the creation flow, what gets
stored in params, and any game screen changes required.

================================
POSITION MASTER
================================

Quiz creation flow:
- Creator picks one letter (A–Z) and one position (1–N)
- Before confirming, the backend validates that enough words exist
  matching that constraint (if 0 or too few, reject with a message)
- Show the creator the word count as feedback
  ("47 words match this constraint") before they finalise
- Title and optional close date as usual

What gets stored in params:
- letter: the chosen letter
- position: the chosen position (1-indexed)

Game screen changes:
- None for Phase 1 — the game already knows how to apply a single
  letter+position constraint. We just pass params.letter and
  params.position instead of randomising.
- locked prop hides mode switching as usual.

Out of scope for now:
- Multi-letter / multi-position constraints (requires new game screen
  validation logic — separate task)
- Mode 2 (dynamic constraints) is not supported in quiz creation;
  quiz always uses Mode 1

================================
LETTER FREQUENCY
================================

Core distinction from Letter Hunt:
- Letter Hunt = presence ("find words containing these letters")
- Letter Frequency = count ("find words where a letter appears exactly N times")
  These are genuinely different constraints and justify separate quiz support.

Quiz creation flow:
- Creator picks one letter (A–Z)
- Optionally picks an exact frequency count (e.g. "appears exactly 2 times");
  if omitted, any frequency is accepted
- Backend validates that enough words exist matching that constraint
  (if 0 or too few, reject with a message)
- Show the creator the word count as feedback before they finalise
- Title and optional close date as usual

What gets stored in params:
- letter: the chosen letter
- count: the required frequency (optional; null means any frequency)

Game screen changes:
- None — the game already knows how to apply a letter frequency constraint.
  We just pass params.letter (and optionally params.count) instead of
  randomising the letter each round.
- locked prop hides mode switching as usual.

Key value over the current game:
- The game today randomises the letter each round. A creator pinning a
  specific letter makes the quiz themeable (e.g. a phonics lesson focused
  entirely on the letter E). That specificity is the quiz's value.

================================
LETTER HUNT
================================

Quiz creation flow:
- Creator enters one or more letters to hunt for (e.g. Q, or S + T + R)
- Backend validates that enough words exist containing all specified letters
  (if 0 or too few, reject with a message)
- Show the creator the word count as feedback before they finalise
- Title and optional close date as usual

What gets stored in params:
- letters: array of letters the player must find words containing

Game screen changes:
- None — the game already applies a letter-presence constraint. We pass
  params.letters instead of randomising.
- locked prop hides mode switching as usual.

Key value over the current game:
- Creator targets specific letters intentionally (e.g. a phonics lesson on
  S, T, R) rather than the game picking at random. Highly useful for
  educational contexts.

================================
LETTER POOL
================================

Quiz creation flow:
- Creator enters the exact set of letters that players will draw words from
  (e.g. A, E, I, R, S, T, N, L)
- Backend validates that enough valid words can be formed from that pool
  (if too few, reject with a message)
- Show the creator the reachable word count as feedback before they finalise
- Title and optional close date as usual

What gets stored in params:
- pool: the exact letter pool (array or string of letters, including duplicates
  if the creator wants a letter available more than once)

Game screen changes:
- None — the game already operates with a given letter pool. We pass
  params.pool instead of generating one randomly.
- locked prop hides mode switching as usual.

Key value over the current game:
- Creator controls which words are even reachable. A carefully chosen pool
  can target specific vocabulary (e.g. only letters from the word TRIANGLE
  forces players into geometry-adjacent words).

================================
DEFINITION MATCH
================================

Quiz creation flow:
- Creator picks a word theme or category (e.g. Science, SAT Prep, Animals,
  Body Parts) from a predefined list we expose
- Optionally picks difficulty level if the game supports it
- Backend confirms that enough words exist in that category
- Title and optional close date as usual

What gets stored in params:
- category: the chosen theme/category slug
- difficulty: optional difficulty level

Game screen changes:
- None — the game already supports category filtering. We pass params.category
  instead of picking randomly.
- locked prop hides mode switching as usual.

Key value over the current game:
- Creator targets specific vocabulary topics, making Definition Match genuinely
  useful as a classroom quiz tool (e.g. "today's quiz: science vocabulary").

================================
WORD ROOTS
================================

Quiz creation flow:
- Creator enters a parent (root) word (e.g. SPLENDID)
- Backend validates: (1) the word exists in our makerWords dataset as a base
  word, (2) it has enough pre-computed derivatives to make a fair puzzle
- Show the creator a preview of the derivatives before they finalise
- Title and optional close date as usual

What gets stored in params:
- baseWord: the creator's chosen parent word
- derivatives: the pre-computed list of valid derivative words for that base

Game screen changes:
- Small addition — if params.baseWord + params.derivatives are present, use
  them directly instead of fetching a random puzzle from the server.
- locked prop hides mode switching as usual.

Key value over the current game:
- Creator curates the exact puzzle. A teacher can pick a root word tied to
  a lesson (e.g.RUPT for words like DISRUPT, CORRUPT, ERUPT). Far more
  intentional than a seed-based random puzzle.

Note:
- Only words already in makerWords are accepted as valid base words. We do
  not dynamically compute derivatives from arbitrary words.

================================
PROGRESSIVE REVEAL
================================

Quiz creation flow:
- Creator enters the target word (e.g. CATHEDRAL)
- Backend validates the word exists in the dictionary
- Title and optional close date as usual
  (no word count preview needed — the word itself is the puzzle)

What gets stored in params:
- word: the creator's chosen target word

Game screen changes:
- Small addition — if params.word is present, use it as the target instead
  of fetching a random word from the server.
- locked prop hides mode switching as usual.

Key value over the current game:
- Essentially a spelling-test mode. Teacher picks the word, players guess it
  letter by letter. Highly specific and intentional — the closest thing to a
  traditional vocabulary quiz in the platform.

================================
LENGTH CHALLENGE (WORD LENGTH)
================================

Background on why all 5 variations have quiz value:
- The game currently randomizes everything — length, letters, all of it. A
  player who wants to practice 6-letter words is at the randomizer's mercy
  and might not get that constraint after dozens of refreshes.
- Even Variation 1 (length only) has real value: the creator guarantees a
  specific length, removing the frustration of random variation selection.
- Variations 2–5 add letter constraints on top of length, which the game
  also randomizes. A creator pinning those letters makes the puzzle
  deliberate and specific rather than arbitrary.

Variations:
  1. Length Only       — randomizes word length (3–8)
  2. Starts With       — randomizes length + starting letter
  3. Ends With         — randomizes length + ending letter
  4. Starts & Contains — randomizes length + starting letter + interior letter
  5. Ends & Contains   — randomizes length + ending letter + interior letter

Quiz creation flow:
- Creator picks a variation (1–5)
- Based on variation, enters the relevant constraints:
    Variation 1: word length only
    Variation 2: word length + starting letter
    Variation 3: word length + ending letter
    Variation 4: word length + starting letter + interior letter
    Variation 5: word length + ending letter + interior letter
- Backend validates that enough words exist matching all specified constraints
  (if 0 or too few, reject with a message)
- Show the creator the word count as feedback before they finalise
- Title and optional close date as usual

What gets stored in params:
- variation: which variation (1–5)
- length: the target word length
- startLetter: starting letter (Variations 2 and 4 only)
- endLetter: ending letter (Variations 3 and 5 only)
- containsLetter: interior letter (Variations 4 and 5 only)

Game screen changes:
- None — the game already knows how to apply all these constraints. We pass
  params values instead of randomising them.
- locked prop hides mode switching as usual.

Key value over the current game:
- Removes the randomizer entirely. Creator guarantees the exact constraint
  set, making the quiz reproducible and intentional for every player.

================================
LETTER BALANCE
================================

Variations:
  Count-based:
    - Consonant Count: words must have an exact number of consonants (levels 2–7)
    - Vowel Count: words must have an exact number of vowels (levels 2–7)
  Position-based:
    - Start & End Vowels
    - Start & End Consonants
    - Start Vowel, End Consonant
    - Start Consonant, End Vowel
  Oblivion (hardest):
    - Consonant Oblivion: exact consonant count + exact word length
    - Vowel Oblivion: exact vowel count + exact word length
  Advanced Mode:
    - Constraint randomizes every word within the chosen variation

Quiz creation flow:
- Creator picks a variation from the list above
- For count-based and oblivion variations, also picks a level (2–7)
- Backend validates enough words exist matching the chosen constraint
- Title and optional close date as usual

What gets stored in params:
- variation: the chosen variation slug
- level: the chosen level (count-based and oblivion only; null for positional)

Game screen changes:
- None — we pass params.variation and params.level instead of letting the
  player choose or the game randomize.
- locked prop hides mode switching as usual.

Key value — two distinct kinds:
- Consistency: for count-based and positional variations, the quiz guarantees
  every player faces the same level/rule rather than each picking their own.
- Specificity: for Advanced Mode, using a seed ensures every player's
  randomized constraint sequence is identical — without this, two players
  in Advanced Mode could face completely different challenges.

Future enhancement (separate task):
- Allow the quiz creator to specify WHICH specific consonants or vowels must
  appear (e.g. "exactly 3 consonants, and they must be B, R, T"). This
  requires new validation logic in the game screen — it does not exist today.
  Same situation as Position Master's multi-constraint idea. Both could be
  built as quiz-exclusive modes that extend the base game.
